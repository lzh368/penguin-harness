# 从训练证据生成有边界的技能

本指南供 Wiki Maintainer、Skill Proposer 和 Companion Auditor 使用。它改进 Penguin 适配中的学习提示，不改变 WikiSkill 的批量训练、单技能提案和独立 validation 严格改善后接受规则。三个角色只读本轮授权的 train 资料及允许的历史资料；不得用 validation/test 逐题内容补证据。

## 1. Maintainer：先记录观察，再归纳模式

先看采样清单和视图说明，确认哪些动作、结果或长输出被截断。GDPevo/Harbor 使用 [training-views.md](training-views.md) 的导出协议，Maintainer 只读清单所选视图；生成视图不证明模型实际读过。视图不能显示所需步骤时，将该解释标为待查；不要把缺失内容当成“Target 没做”。系统提示词、工具说明和上轮已注入技能是输入条件，不是本轮新经验。Proposer 阅读完整 raw 时也须区分任务行为与引擎控制记录：上下文压缩期间的工具请求可能根本未执行，其合成错误不能当成工具真实失败的证据。

围绕每个有用的模式记录：

- **条件与观察**：当时任务要求是什么，Target 执行了什么，可见结果是什么。引用 train 入口及对应消息、行号或事件位置，不只写“见四条 evidence”。
- **解释与状态**：哪些是直接观察，哪些是可能原因。一次低分不能定位失败动作；一次满分不能证明其中每一步都必需。基础设施故障不归纳为业务规则。
- **建议行为与边界**：在何种可观察条件下可尝试什么动作；哪些已读记录不符合，哪些关键场景尚无证据。
- **来源与演变**：保留支持和冲突证据；新证据削弱旧规则时收窄或撤销原结论，不能只在另一文件加一句相反建议而让索引仍推荐旧规则。

同一机制合并重复模式。不同任务表面词汇相近不代表机制相同；适用条件可以是任务结构或工具行为，不必机械按领域划分。尚未确定的推测可以留在 Wiki，但要让 Proposer 能区分“值得查证”与“可直接写入技能”。没有新结论时记日志即可。

### 合成例子：避免从现象跳到通用规则

训练轨迹 A：保存表格后重新打开，发现公式引用偏移；Target 修复了引用。轨迹 B：只读分析表格，没有保存动作，结果正常。

可记录的模式是“表格写入后可能出现序列化或引用变化，保存后复查可能及时发现问题”。不能归纳为“所有表格任务必须保存并重新打开”，也不能仅凭 A 的分数断言这一步一定提高成绩。B 是跳过写入复查的边界。若未读到 B，应记“只读场景未观察”，不能虚构一条成功对照。

## 2. Proposer：一项改动对应一个可检验假设

先用 Wiki 和训练摘要定位一个行为缺口，再读取至少四个本轮不同任务的完整轨迹。优先覆盖问题出现、未出现或现有行为已成功的相关情形；对照必须来自实际可读的 train 数据，没有合适对照时如实说明。完整阅读包括轨迹入口列出的全部分片和子轨迹；抽样视图或前若干行不能代替。

改动前比较现有技能：重复规则不再添加；相互冲突的条件应在所修改的技能中澄清。若修正需要同时改多个技能，本轮仍只能提出一个合法局部修改，或说明为何暂时 no_action。不要在一个新技能里打包若干无关的业务猜测。

对实际新增或收紧的每条行为规则，在 `PURPOSE.md` 留下简短论证。格式可以自然表达，但应覆盖：

| 要说明的内容 | 应回答的问题 |
|---|---|
| 改动与预期作用 | Target 会在哪一步改变动作？预计修复哪类训练中可见的问题？ |
| 支持证据 | 哪个 train 入口的哪段观察支持它？是直接事实还是尚待验证的机制假设？ |
| 启用与跳过条件 | Target 在新任务中能观察什么条件来决定使用？哪些情况下保持原做法？ |
| 反证与不确定性 | 实际查到哪些冲突、成功对照或未覆盖情形？为什么当前范围仍值得验证？ |
| 与旧技能的关系 | 增补、收窄还是替换哪一条旧行为？历史拒绝后此次实质改变是什么？ |

证据定位、case ID、历史分数和演变说明留在 PURPOSE；它们不属于 Target 的解题指令。原始材料无须复制进 PURPOSE。`proposal.evidence` 仍使用现有完整轨迹入口协议，不增加 JSON 字段。

### Target 实际收到的 SKILL

本适配会完整注入全部活跃技能，因此**技能名称或 description 并不能阻止正文在不相关任务上生效**。正文开头写出可识别的适用条件和不适用时的行为，再给必要步骤及停止条件；不能把边界只写在 PURPOSE。

- 条件应依赖当前任务可观察的要求、输入结构或工具状态，不依赖“训练时这题得过高分”或某个隐藏类别。
- 优先保留能解释预期作用的最少步骤。不把常识、重复提醒和互不相关的检查堆成大型清单；新增动作也会消耗时间或干扰已有正确流程。
- 学到的经验不能替代当前任务明确给定的约束。训练未确定的数据优先级、业务阈值、匹配条件或必需字段，不能由 Proposer 自行发明成跨任务规定。
- 对未知情形保留原有任务判断，或做任务允许的低成本核查。不要无条件换工具、改输入、写文件或舍弃数据。

上面的合成例子可以生成“仅在本任务要求修改并保存表格时，保存后检查受影响公式；只读分析跳过此步骤”，而不是要求所有表格任务执行保存。这仍只是可验证的候选，不是已经证明有效的技能。

## 3. Auditor：核对论证和实际边界

沿真实 diff 检查新增或收紧的行为规则，至少追踪到 PURPOSE 的引用与原训练观察；同时核对 Proposer 读取记录确实覆盖四个不同任务的完整轨迹。路径存在、哈希正确只证明材料身份，不证明模型读过，也不证明规则成立。

- 已提供完整证据但技能明显违背其中条件、忽略已读反例、扩大为无依据的必然规则，或夹带具体答案：报告具体冲突，`fail`，由 Proposer 在 stage 前修正。
- 引用缺失、轨迹读取不完整、截断使关键观察无法核对：`unverified`，说明要补的材料，不补造 pass。
- 范围已限定、论证可追溯但效果仍不确定：可通过合法性审计，并把不确定性作为 warning 留档；效果交给固定 validation。没有对照不自动等于无效，也不能虚构对照来通过审核。

审计不创建更好的技能，不挑选 validation/test 有利任务，不提高或降低接受阈值。候选拒绝后保留 Wiki、论证和差异，由后续训练决定是否有新的修正依据。
