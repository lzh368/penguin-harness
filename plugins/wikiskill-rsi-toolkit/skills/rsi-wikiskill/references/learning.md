# 从训练证据生成有边界的技能

本指南供 Wiki Maintainer、Skill Proposer 和 Companion Auditor 使用。它改进 Penguin 适配中的学习提示，不改变 WikiSkill 的批量训练、单技能提案和独立 validation 严格改善后接受规则。三个角色只读本轮授权的 train 资料及允许的历史资料；不得用 validation/test 逐题内容补证据。

## 1. Maintainer：先记录观察，再归纳模式

先看采样清单和视图说明，确认哪些动作、结果或长输出被截断。GDPevo/Harbor 使用 [training-views.md](training-views.md) 的导出协议，Maintainer 只读清单所选视图；生成视图不证明模型实际读过。视图不能显示所需步骤时，将该解释标为待查；不要把缺失内容当成“Target 没做”。系统提示词、工具说明和上轮已注入技能是输入条件，不是本轮新经验。Proposer 阅读完整 raw 时也须区分任务行为与引擎控制记录：上下文压缩期间的工具请求可能根本未执行，其合成错误不能当成工具真实失败的证据。

围绕每个有用的模式记录：

- **条件与观察**：当时任务要求是什么，Target 执行了什么，可见结果是什么。引用 train 入口及对应消息、行号或事件位置，不只写“见四条 evidence”。
- **解释与状态**：哪些是直接观察，哪些是可能原因。一次低分不能定位失败动作；一次满分不能证明其中每一步都必需。基础设施故障不归纳为业务规则。
- **建议行为与边界**：在何种可观察条件下可尝试什么动作；哪些已读记录不符合，哪些关键场景尚无证据。
- **来源与演变**：保留支持和冲突证据；新证据削弱旧规则时收窄或撤销原结论，不能只在另一文件加一句相反建议而让索引仍推荐旧规则。

同一机制合并重复模式。不同任务表面词汇相近不代表机制相同；适用条件可以是任务结构或工具行为，不必机械按领域划分。尚未确定的推测可以留在 Wiki，但要让 Proposer 能区分“值得查证”与“可直接写入技能”。没有新结论时记日志即可。

同样的推断或操作若同时出现在高分、低分任务中，应一并记录，不能把高分任务描述成“没有该问题”的对照。整题分数之间的排序不能证明某个步骤造成失分。索引中的简短结论也要保留这个限制，避免 Proposer 只读索引就继承错误前提。模式页优先写清问题、已知原因或尚待查证的解释、可尝试的具体操作；包含必要的命令或计算片段，参数由新任务提供，不把题目答案复制进去。

分别标明任务明确要求、工具返回的事实和 Target 自行作出的解释。Target 在推理中称某字段“干扰项”，只是一次判断，不能直接升级为 Wiki 的通用事实。“不要照抄现有值”要求核查，不等于“忽略这个字段”；要记录核查需要哪些来源，以及哪些条件下仍须保留原信息。标题、索引摘要和模式页保持相同的适用范围与不确定性，不能正文写“待验证”，标题却下确定结论。

### 先核对完整过程，再命名模式

对选中的训练任务，在 Wiki 中用短表或短段串起“任务要求 → 相关输入/规则 → 实际动作或计算 → 交付结果 → 已知反馈”，每项附可见证据位置。重点查找证据链中最早能确认的偏差：未取得数据、规则解释错误、计算或操作错误、交付不符合要求。不要因为最后看见一次检查或格式修正，就把它当成全部失分的原因；没有足够材料时写明断点，留给 Proposer 查完整轨迹。

检查中间失败后是否发生修正，并读到实际提交或最终可见产物。区分“尝试过但放弃的方案”“后来纠正的错误”“最终仍存在的问题”。不能把中间的空结果、报错或暂定公式写成最终答案；材料没有展示最终产物时写明未知。轨迹中已经完成的修正可以成为可复用经验，不必为了提出技能而说成尚未修复。

连续分数不能把任务分成“全对”和“什么都没学到”两类。采样用的 failure 只表示未满分：保留轨迹里有证据的正确子步骤、局部失败和可复用操作。没有满分样本也能提出候选；但一个高分任务的所有步骤不自动正确，低分任务的所有步骤也不自动错误。`score_only` 下只能据题面、可见业务规则、实际输入输出和显式工具错误诊断，不能从总分反推隐藏评分项、标准答案或某一步的得分。

提炼内容可以是业务操作方法，例如根据当前任务提供的规则表完成匹配、推导、计算和核对。它不必局限于“多搜一些”“检查 JSON”这样的流程提醒。提取可迁移的运算和决策步骤，参数、阈值及来源优先级仍由新任务的明确要求决定；不要把训练题某个常量或答案复制成规则。

### 合成例子：避免从现象跳到通用规则

训练轨迹 A：保存表格后重新打开，发现公式引用偏移；Target 修复了引用。轨迹 B：只读分析表格，没有保存动作，结果正常。

可记录的模式是“表格写入后可能出现序列化或引用变化，保存后复查可能及时发现问题”。不能归纳为“所有表格任务必须保存并重新打开”，也不能仅凭 A 的分数断言这一步一定提高成绩。B 是跳过写入复查的边界。若未读到 B，应记“只读场景未观察”，不能虚构一条成功对照。

## 2. Proposer：一项改动对应一个可检验假设

先用 Wiki 和训练摘要列出可复用做法及待查的行为缺口，再读取至少四个本轮不同任务的完整轨迹，查证后才确定本轮要改哪一点。优先覆盖问题出现、未出现或现有行为已成功的相关情形；对照必须来自实际可读的 train 数据，没有合适对照时如实说明。完整阅读包括轨迹入口列出的全部分片和子轨迹；抽样视图或前若干行不能代替。阅读与预算冲突时报告未完成，不能用“已读四条”替代实际覆盖。

在已读材料中比较候选方向：哪种偏差有直接证据、在多少种任务条件下出现、拟议动作能改变哪一步、会增加多少操作或干扰哪些正确步骤。比较两种方向：把已经观察到的有用做法编译成可复用指令，或修正有证据的行为缺口。两者都可以提出，不强制新动作必须不同于每条训练轨迹中的做法，也不要求凑多个成功案例。编译已有做法时说明它如何执行、适用范围及为何值得稳定复用；不得把“以前已经做过”改写成“以前没做”。检索、格式和收尾检查并不天然优先；如果记录已包含所需输入，而错误发生在后续计算，必须说明增加检索如何帮助该计算，否则换一个有依据的方向。一个现象可以有多个解释，例如返回条数相同可能是分页、过滤或真实数据量，不得把猜测写成必然规则。

改动前比较现有技能：重复规则不再添加；相互冲突的条件应在所修改的技能中澄清。若修正需要同时改多个技能，本轮仍只能提出一个合法局部修改，或说明为何暂时 no_action。一个机制可以需要多个相连步骤，但只写进同一个文件不等于只有一个机制。优先选择一条有依据、能实际影响解题的操作链；不要把检索、若干业务判断和格式检查拼成通用总清单。辅助步骤应能说明如何服务所选机制。

对实际新增或收紧的每条行为规则，在 `PURPOSE.md` 留下简短论证。格式可以自然表达，但应覆盖：

| 要说明的内容 | 应回答的问题 |
|---|---|
| 改动与预期作用 | 是编译已观察到的做法，还是修正行为缺口？哪些步骤将成为明确指令？ |
| 支持证据 | 哪个 train 入口的哪段观察支持它？是直接事实还是尚待验证的机制假设？ |
| 启用与跳过条件 | 入口条件成立后，每个必需步骤的输入是否具备？哪些分支只在额外条件成立时执行，哪些情况下保持原做法？ |
| 反证与不确定性 | 实际查到哪些冲突、成功对照或未覆盖情形？为什么当前范围仍值得验证？ |
| 与旧技能的关系 | 增补、收窄还是替换哪一条旧行为？历史拒绝后此次实质改变是什么？ |
| 训练内推演 | 在已读记录上，规则会复用或改变哪一步，依据什么输入得到什么中间结果？实际最后提交了什么，原有正确步骤是否保持？ |

证据定位、case ID、历史分数和演变说明留在 PURPOSE；它们不属于 Target 的解题指令。原始材料无须复制进 PURPOSE。`proposal.evidence` 仍使用现有完整轨迹入口协议，不增加 JSON 字段。

### 提案前，用现有训练记录检查规则是否可执行

这一步是证据推演，不重新调用 Target，不提交 judge，不增加同题试分或候选数量。PURPOSE 至少展开一处实际已读训练记录，按“可见条件 → 实际动作与最终产物 → 要编译或修正的步骤 → 可核对的中间结果/尚未知的结果”对应到 SKILL 步骤。没有私有标签时可以不知道正确答案或得分，但应能核实操作的输入来源、计算/查询/判断方式，以及它如何影响后续解题。只列四条 evidence 或写“应该更准确”不构成推演。

再检查另一个已读场景：入口条件是否触发、每个必需步骤是否有相应输入或允许的获取途径、是否会破坏原来正确的操作。尤其检查同领域但任务要求不同的记录，不能仅因名称相近就沿用同一套字段和决策。发现适用范围过宽时收窄入口，或在具体步骤前补充可观察的分支条件；没有合适场景则注明未覆盖，不编造反例，也不要求穷举所有未来任务。推演不等于实测分数。

如果规则在所有支持场景里都不会触发，需要补充依据或 no_action。Target 已经执行了相同步骤时，可以诚实地将其作为经验编译；不能声称修复了该记录并不存在的遗漏。只有当前 accepted Skill 已完整覆盖相同规则、又没有实质修改时，才按重复提案处理。条件与动作合理而效果未知的候选可交 validation 检验，不以缺少成功对照为由一律拒绝。

以下情况分开处理：

- **编译已有做法**：Target 曾主动核对规则、发现偏差并修正，或完成了可核对的计算。可以把该过程缩成带边界的操作指令；说明该次已执行，预期作用是帮助后续任务复用，不声称修复该次最终答案。是否提高稳定性仍需 validation。

- **有操作，收益未知**：依据公开规则重新计算一个中间量、补充一项有明确用途的查询，或用一致性检查发现冲突并据此修正后续步骤。允许作为候选；不要求先证明提分。
- **只有解释变化**：原来猜一个值，现在仍猜同一个值、只加一句“待确认”；若任务未要求不确定性报告，也没有后续查询或分支变化，尚未给出改善解题的操作。先补正或 no_action，不用“效果未知”代替操作方案。
- **替换成另一种猜测**：仅因字段同名就复制、遇到歧义一律相信模板、默认采用最简单映射。这些不是查证方法；缺少当前任务的语义、单位、范围或权威性依据时，不能写成通用必然规则。需给出明确的核对方法，或收窄到已有依据的场景。

这不禁止领域推理，也不要求每条规则都在题面逐字出现。可以用当前任务的说明、数据关系、工具反馈和适用的领域知识形成假设，再用任务允许的证据核查。若规则仍无法确定，保留 Target 的任务判断并标注限制；不要强制使用同名字段、删掉无法确定的输出，或仅因没有标准答案就禁止提出任何候选。

### 输出格式与决策依据分别核对

输出模板可能同时包含结构约束和明确的业务定义；逐项读其含义，不能假定模板列出了全部输入或决策规则。某个源字段未出现在输出键或枚举中，不证明它无关。例如任务只输出一个汇总金额，输入明细的币种和单位仍可能决定计算。反过来，同名字段也不证明可以直接复制；核对任务定义、单位、时间和实体关系。

学到的规则应写出如何核对证据，而不是预设某类来源永远可信或永远应忽略。区分“未查到”“未核实”和“已有反证”，缺少证据不自动等于相反结论。若拟议操作依赖业务阈值、来源优先级或状态转换条件，说明从当前任务哪里取得；未知时用允许的证据核查，仍未知则保留任务判断，不能将训练中的猜测变成强制默认值。

### 合成推演：从提醒变为计算步骤

以下仅用于说明提案质量，不是任何 benchmark 的答案，不得直接写入正式提案。

假设训练题明确要求“按账户汇总尚未结清金额”。记录 A 的两行数据中，原金额为 100、60，已结清金额为 40、10；Target 直接累计原金额得到 160。候选步骤可以是：按任务给定的结清定义逐行计算未结清金额，再按账户汇总，并核对原金额合计等于已结清与未结清之和。该记录上中间量为 60、50，汇总为 110，核对为 160 = 50 + 110。算式能从公开输入验证，不需要读取评分答案，也不能据此声称整题得分一定提高。

记录 B 若本来就按相同定义算出了未结清金额，技能应直接复用并核对结果，避免重复计算。若另一任务明确要求原金额，适用条件应使技能跳过，不能强行减去结清金额。

对比而言，“汇总前多检查一下”没有给出可执行操作；“所有金额都先减已结清金额”忽略适用条件；“字段同名就直接复制”没有核实含义。这三种写法都需要修正。有效的检查类技能可以保留，但必须说明检查什么、怎么检查、发现不同结果后改哪一步。

第二轮及以后，用当前 accepted 的正文和本轮 train 轨迹核对：规则是否触发、Target 是否执行、执行后可见的问题是什么。区分未触发、未遵循、已遵循仍有缺口、证据不足，再决定收窄、澄清或修正哪一步。历史 validation 汇总只说明整体接受或拒绝，不能定位业务错误；拒绝后重提需要训练中的新证据或实质改动，不能仅换名称或改措辞。

### Target 实际收到的 SKILL

本适配会完整注入全部活跃技能，因此**技能名称或 description 并不能阻止正文在不相关任务上生效**。正文开头写出可识别的适用条件和不适用时的行为，再给必要步骤及停止条件；不能把边界只写在 PURPOSE。

- 条件应依赖当前任务可观察的要求、输入结构或工具状态，不依赖“训练时这题得过高分”或某个隐藏类别。
- 优先保留能解释预期作用的最少步骤。不把常识、重复提醒和互不相关的检查堆成大型清单；新增动作也会消耗时间或干扰已有正确流程。
- 适用范围覆盖每个必需步骤。特定业务字段或工具只放在条件明确的分支中；条件不成立时明确跳过，不能让 Target 自行猜测哪些必需检查其实不适用。
- 学到的经验不能替代当前任务明确给定的约束。按上面的证据核对方法确定输入与规则；不能只在结尾写“以当前任务为准”，却在前文规定无条件的来源优先级、业务阈值或必需字段。
- 对未知情形保留原有任务判断，或做任务允许的低成本核查。不要无条件换工具、改输入、写文件或舍弃数据。
- 每个主要步骤写清所需输入、如何处理、产出什么以及何时停止；“认真分析”“全面检查”不能单独构成技能。已有正确结果无需为执行技能而重做。只对当前任务允许修改的范围执行写操作。

上面的合成例子可以生成“仅在本任务要求修改并保存表格时，保存后检查受影响公式；只读分析跳过此步骤”，而不是要求所有表格任务执行保存。这仍只是可验证的候选，不是已经证明有效的技能。

## 3. Auditor：核对论证和实际边界

沿真实 diff 检查新增或收紧的行为规则，至少追踪到 PURPOSE 的引用与原训练观察；同时核对 Proposer 读取记录确实覆盖四个不同任务的完整轨迹。路径存在、哈希正确只证明材料身份，不证明模型读过，也不证明规则成立。

- 已提供完整证据但技能明显违背其中条件、忽略已读反例、扩大为无依据的必然规则，或夹带具体答案：报告具体冲突，`fail`，由 Proposer 在 stage 前修正。
- 引用缺失、轨迹读取不完整、截断使关键观察无法核对：`unverified`，说明要补的材料，不补造 pass。
- 范围已限定、论证可追溯但效果仍不确定：可通过合法性审计，并把不确定性作为 warning 留档；效果交给固定 validation。没有对照不自动等于无效，也不能虚构对照来通过审核。

另外核对训练内推演：触发条件在引用记录中是否可观察，提案是否如实区分复用与修正，中间结论是否能从当时可用的输入导出，引用是否与实际最终产物一致。将“只解决检索/格式，但声称修复计算/业务决策”的断链指出来；补充新操作必须说明其作用。明显不触发、把已做步骤谎称遗漏、把已放弃的中间方案谎称最终交付、或与明确任务约束冲突时 fail；有合理作用但增益未知时 warning，不冒充性能裁判。

### 审计前提与收益不确定性分别判断

对提案的主要操作逐项核对，记录具体证据，不能因为已读满四条、文件齐全或 PURPOSE 自称“待验证”就通过：

| 观察到的情况 | 审计处理 |
|---|---|
| 编译已有做法或修正缺口，操作明确、依据可查、中间结果可核对，最终收益未知 | 可 `pass`；收益未知可记 warning，交 validation 检验 |
| 没有展开具体训练场景，无法核实操作依据或对应 SKILL 步骤 | `unverified`；列出要补的推演，不进入 stage |
| Target 已做过同一操作，提案如实作为经验编译，且当前 accepted Skill 尚未覆盖 | 可 `pass`；不得额外要求发明新动作或先证明提分 |
| 把后来纠正的中间错误说成最终输出的错误 | `fail`；纠正 Wiki/PURPOSE 的事实前提后再审计 |
| 训练内已明确仅改备注/措辞，未改变任务要求的输出或处理流程，却声称修复计算或判断 | `fail`；要求修正作用机制或 no_action |
| 无依据地规定同名复制、模板优先或业务阈值，即使仅在歧义场景触发 | `fail`；触发范围有限不等于规则已有依据 |
| 入口包含已读训练场景，但其中必需步骤的输入或业务条件不成立，又没有明确的跳过分支 | `fail`；先收窄入口或修正该步骤，不能靠“遵守当前任务”的总括声明放行 |
| 将“输出模板没列出某源字段”作为忽略该信息的充分理由，或将 Target 的一次解释写成固定来源优先级 | `fail`；须给出查证方法及有依据的适用范围 |
| 证据说明把有同类行为的高分样本误写成“没有该行为”的对照 | `unverified`；先纠正 Wiki/PURPOSE 中的事实前提；若规则本身已与证据矛盾则 `fail` |

审计针对可指出的事实矛盾和执行缺口，不把未知收益或尚未观察的任务类型一律判失败。输入可通过合法查询取得时，不因它尚未读取就认定步骤不适用。缺少业务前提、会改变输出的范围冲突须先修正；拼写、重复标题等不改变动作和证据含义的问题可以记 warning。PURPOSE 里的限制须落实在 Target 收到的 SKILL 步骤中，“这是待验证假设”不免除对已知冲突的修正。

被指出的关键缺口必须在 stage 前解决。审计员只指出缺口，不代写候选；Controller 让原学习角色依据 train 材料修订并重新审计，保留原稿和回执。不能通过看 validation/test 内容来补理由，也不能先试分再倒写解释。修订仅解决合规和依据问题，不增加隐藏的候选搜索或训练试分。工具不支持保留版本的修订时停止，不让 Controller 覆盖文件。

审计不创建更好的技能，不挑选 validation/test 有利任务，不提高或降低接受阈值。候选拒绝后保留 Wiki、论证和差异，由后续训练决定是否有新的修正依据。
